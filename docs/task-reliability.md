# 任务受理幂等、断点续跑与自动重试

日期：2026-11-02。本文记录本次提交的扩展方案与实现；此前并发和事务基线为 `730d70d`。本轮实现、迁移、测试与本文档一并提交；提交定位方式见根目录 README 的验收版本说明。

## 目标与方案选择

在保留三阶段顺序、数据库持久化和最终状态不回退的前提下，解决三类问题：提交响应丢失后的重复受理、进程中断后的阶段恢复，以及暂时性故障的有限重试。

| 问题 | 备选方案 | 本次选择与原因 |
| --- | --- | --- |
| 受理去重 | 浏览器按钮锁、进程内缓存、Redis 锁、数据库唯一约束 | 用户＋幂等键的数据库唯一约束，受理与幂等记录在同一事务，不引入另一个存储系统；按钮锁继续作为交互保护 |
| 受理竞争 | 先查再插、捕获唯一冲突后续查、按用户串行化受理 | 沿用已有账户行锁，再查唯一键；同一账户的并发受理短事务串行化，避免在已回滚事务中处理唯一冲突。数据库唯一索引作为最后约束 |
| 恢复粒度 | 整任务重做、阶段检查点、引入独立工作流引擎 | 复用 task_step 的成功阶段为检查点，三个阶段无需额外编排服务；未提交的阶段允许重做，不承诺从某条指令或某毫秒继续 |
| 失败处理 | 内存中 sleep 重试、单纯注解重试、数据库保存执行计划 | 在数据库保存下次执行时间和尝试预算；进程重启不会丢失退避计划，也不占用工作线程等待重试 |
| 执行权 | 启动时将全部 RUNNING 失败、仅检查进程、租约与执行令牌 | 只接管过期租约，心跳保护长阶段；令牌和任务行锁阻止旧执行者在接管后提交 |
| 重试策略 | 无限重试、每阶段独立预算、每任务总预算 | 默认总计 3 次执行，包含首次、自动重试和中断恢复。指数退避有上限；确定性失败立即终止，防止坏任务无限循环 |

本次不增加 MQ、Redis 或工作流引擎。以当前规模采用可重复观察的确定性退避；没有加入随机抖动。大规模部署可另行评估调度吞吐、抖动、配额和外部工作流需求。

## 受理幂等协议

`POST /api/tasks` 支持 `Idempotency-Key` 请求头。为兼容旧调用，头可省略，但省略时不提供重复受理保护；网站始终发送该头。

键须满足 `[a-z0-9][a-z0-9._:-]{0,127}`。数据库以 `(owner_id, idempotency_key)` 唯一索引隔离账户。使用不可复用的随机键表示一次新的制作意图，不能用 templateId 或素材列表作为所有制作共用的键。

| 请求 | 行为 |
| --- | --- |
| 新键、合法参数 | 在同一受理事务写入任务、参数指纹、素材顺序和三个步骤；202 返回 taskId |
| 同一用户、同键、相同参数 | 返回原任务 ID 及其当前状态，`Idempotency-Replayed: true`；即使已成功或失败，也不创建新任务、不重置重试次数 |
| 同一用户、同键、参数不同 | 409，`IDEMPOTENCY_CONFLICT` |
| 不同用户使用同一个键 | 独立作用域，各自验证资源归属 |
| 受理事务回滚 | 幂等键与任务一起回滚，可以用原键重新提交 |

指纹是解析后的规范化请求的 SHA-256：JSON 字段顺序及空白不影响结果，素材数组顺序有意义。缺省失败阶段归一为 NONE，缺省暂时故障次数为 0；省略的耗时与显式提供的耗时仍是不同参数。指纹不依赖之后的后端默认值或模板修改，因此重放不会重新校验已受理素材文件或更换任务快照。以后变更指纹规则时，必须兼容已经保存的键和指纹。

键随任务保留，没有自动 TTL；删除账户及任务后不继续保留该去重记录。客户端必须在得知受理结果之前保存并复用键，不能每次网络重发都生成新键。

网站按账户和模板将尚未确认的请求及随机键保存到当前标签页 sessionStorage：刷新后可“恢复上次提交”；202 确认后清除，新一次主动提交生成新键。浏览器存储不可用时仅保留内存恢复能力。关闭标签页或清理存储会失去本地意图，应先查历史；清除恢复记录不取消服务器任务。网站不会无提示地将未确认请求替换成另一组参数。

## 数据模型与事务

Flyway V7 增加以下持久化内容：

- production_task：幂等键和指纹、attempt_count/max_attempts、退避参数快照、next_attempt_at、lease_token/lease_expires_at、上次执行错误、暂时故障模拟配置。
- task_step.attempt_count：该阶段被启动的次数；成功阶段的时间和计数在后续恢复中保留。
- task_attempt：每次认领的编号、内部令牌、阶段、起止时间、结果和错误；以 task_id/attempt_no 为主键，随任务级联删除。

受理时固定最大尝试次数及退避参数；后续修改服务器重试默认值不改变已受理任务的预算。租约及心跳周期属于当前执行环境配置。V7 之前的历史不回填虚构的尝试记录，历史阶段计数可能为 0。

认领事务同时更新 RUNNING、执行令牌、租约、尝试次数、当前步骤及尝试记录。阶段完成事务同时提交步骤检查点、当前阶段、版本与尝试阶段；最终结果仍按 V6 方案与 SUCCEEDED 状态一并提交。失败事务同时保存尝试结果，并选择排队或最终失败。任何 SQL 失败均回滚本次迁移，不提交半套步骤、结果或审计记录。

## 状态、检查点和执行权

整体状态仍为 QUEUED、RUNNING、SUCCEEDED、FAILED：

```text
QUEUED（首次等待或退避等待）
  → 到达 next_attempt_at 后认领 RUNNING，生成新的执行令牌
  → 阶段成功：提交检查点，再进入下一阶段
  → 全部完成：SUCCEEDED
  → 可恢复错误且预算未用完：QUEUED，保留当前阶段，安排下次执行
  → 明确失败或预算耗尽：FAILED
```

认领时只从当前检查点启动，之前的步骤必须均为 SUCCEEDED。重试只重置未完成的当前步骤，后续仍为 PENDING；最终失败后后续步骤为 SKIPPED。

默认租约 120 秒、心跳 1 秒。工作线程每阶段前续租；调度器另行心跳续租，防止阶段耗时超过租约。启动和每轮调度只扫描过期 RUNNING，不终止仍持有有效租约的执行者。过期后将旧尝试记为 LEASE_EXPIRED，并按同一总预算安排恢复；启动扫描暂时失败会交给后续调度重试。

阶段提交和错误处理都要校验状态、内部令牌与租约期限，且先锁任务行；旧令牌不能续租、提交步骤或把新执行者的任务标为失败。令牌不返回给浏览器。接管前可能同时存在旧计算与新计算，但只有有效执行者能提交数据库状态。

因此提供的是有预算、可恢复的“至少一次执行”语义，不宣称所有计算只发生一次。模拟检查和预置图片生成可重复；若接入外部 AI/支付等副作用，必须使用稳定的 taskId＋stage 操作键、外部幂等接口或事务消息等方案。租约不能撤销已经发出的外部请求，也不能使 MySQL 与文件系统形成分布式 ACID。

## 自动重试分类与退避

可重试：模拟暂时故障、Spring 暂时性/可恢复数据库异常、数据库连接暂不可用、阶段 IO 异常及执行线程中断。最终提交实际已成功但客户端得到异常时，后续错误处理会看到终态，不把成功改回排队或失败。

不自动重试：参数和权限错误、素材缺失/损坏、预置生成资源缺失、明确指定的 failAtStage 失败，以及不被识别为暂时性故障的程序错误。查询网络异常只影响查询，不消耗后台执行预算。

退避公式为 `min(retryMaxDelayMs, retryBaseDelayMs × 2^(attemptCount−1))`。默认最大执行 3 次，所以首次故障后等待约 1 秒，第二次约 2 秒，第三次仍失败则结束。等待存于 next_attempt_at，不由工作线程 sleep 实现。重启和数据库暂时不可用后仍能按持久化计划处理；终态不会自动复活。

最终耗尽返回 FAILED / RETRY_EXHAUSTED，并保留 lastErrorCode/lastErrorMessage 及尝试历史。预算按任务全局计算，某阶段成功不会重置预算；反复崩溃也消耗执行次数。

## 接口与演示

原有提交和查询路径不变，任务查询额外返回：attemptCount、maxAttempts、nextAttemptAt、lastErrorCode、lastErrorMessage、attempts，以及每步骤 attemptCount。attempts 的结果含 RUNNING、SUCCEEDED、RETRY_SCHEDULED、LEASE_EXPIRED、FAILED。页面会显示等待恢复/重试、执行次数和详细尝试记录。

使用已上传素材的例子：

```http
POST /api/tasks
Idempotency-Key: production-intent-001
Content-Type: application/json
Cookie: material_session=<当前会话>

{
  "templateId": "demo-pet",
  "assetIds": ["上传接口返回的 assetId"],
  "simulation": {
    "failAtStage": "NONE",
    "materialCheckDelayMs": 100,
    "mockGenerationDelayMs": 100,
    "resultAssemblyDelayMs": 100,
    "transientFailAtStage": "MOCK_GENERATION",
    "transientFailureCount": 1
  }
}
```

保持请求体与键不变重发，应返回同一 taskId；改变请求体应为 409。暂时故障次数为前 N 次任务执行中，在指定阶段发生暂时故障；范围 0～5，需配合实际 maxAttempts 判断能否最终成功。原 failAtStage 保持确定性直接失败，不通过无限重试掩盖。

网页操作：展开演示控制，设置“暂时故障位置”和次数；默认预算下次数 1 可恢复成功，次数 5 会耗尽。不要同时指定直接失败阶段来观察简单的暂时故障场景。详情可展开“执行尝试记录”。

PowerShell 7 API 脚本增加以下用法；脚本在一次运行内重复同一受理请求，并自动检查最终状态：

```powershell
pwsh -File backend/scripts/demo.ps1 -ReplayAcceptance
pwsh -File backend/scripts/demo.ps1 -TransientFailAtStage MOCK_GENERATION -TransientFailureCount 1 -DelayMs 100 -ReplayAcceptance
pwsh -File backend/scripts/demo.ps1 -TransientFailAtStage RESULT_ASSEMBLY -TransientFailureCount 5 -DelayMs 100
```

## 断点续跑演示

仅在专用本地演示项目中操作。复制 .env.example 为被 Git 忽略的 .env.retry-demo，为前端、Java、MySQL 设置独立端口和对应 ALLOWED_ORIGINS，并将 TASK_LEASE_MS 设为 5000、TASK_HEARTBEAT_INTERVAL_MS 设为 1000：

```sh
docker compose -p retry-demo --env-file .env.retry-demo up -d --build --wait
```

登录并提交生成耗时 15000 ms 的任务，在详情确认素材检查成功、进入模拟生成后，仅终止这个专用项目的后端：

```sh
docker compose -p retry-demo --env-file .env.retry-demo kill -s SIGKILL backend
docker compose -p retry-demo --env-file .env.retry-demo start backend
```

重启后重新登录相同账户查看历史。有效租约会等待到期，之后按退避计划接手；已成功的素材检查时间和次数不变，执行记录出现 LEASE_EXPIRED 和后续成功。使用默认 120 秒租约时，恢复等待会更长。演示完成使用相同项目名和配置执行 docker compose down，保留数据卷。

## 配置、迁移和回滚

| 变量 | 默认与约束 |
| --- | --- |
| TASK_MAX_ATTEMPTS | 3，总计执行次数，1～6 |
| TASK_RETRY_BASE_DELAY_MS | 1000，至少 1 ms，不大于上限 |
| TASK_RETRY_MAX_DELAY_MS | 30000，至少等于基础等待，最大 300000 ms |
| TASK_LEASE_MS | 120000，3000～3600000 ms |
| TASK_HEARTBEAT_INTERVAL_MS | 1000，至少 100 ms，严格小于租约的一半 |

这些变量已接入 .env.example 和 Compose。并发、扫描周期仍沿用原配置。示例短租约仅用于隔离验收，日常默认保留 120 秒。多台服务器应同步时钟；多个 Java 实例还需共享素材存储、处理服务端会话路由，当前没有完成完整集群部署验收。

升级前停止旧后台执行者，备份数据库与文件卷，再构建启动新版本；Flyway 自动执行 V7。不要混合运行不理解租约的旧版本。旧 QUEUED 从原阶段进入新执行流程；旧 RUNNING 无租约，按过期检查点恢复；旧终态保留。V7 的既有任务默认预算为迁移给定的 3 次，新受理任务才采用当前配置快照。

不能直接降级到只理解 V6 的执行程序：它无法解释保留阶段的退避队列、尝试历史和租约。回滚应使用兼容这些字段及状态的代码，或在维护窗口从配套备份恢复；V6 新结果格式的原有兼容限制同样适用。
